## 1. Мета проєкту та концепція

Трансформація заводського монітора якості повітря Honeywell HTRAM на повністю автономний, відкритий та преміальний IoT-пристрій для екосистеми **Home Assistant**:
1. **Повна незалежність від хмар та сторонніх проксі:** Нативна інтеграція з Home Assistant через нативний протокол **ESPHome (Native API)** без сторонніх MQTT-брокерів і TLS-сертифікатів.
2. **Преміальний графічний інтерфейс (UI/UX):** Відмова від примітивного текстового термінала на користь професійного інтерфейсу на рушії **LVGL** (напівпрозорий хвилеподібний графік CO₂ на тлі, адаптивні кольори теми «зелений / бурштин / рубін», згладжені шрифти, іконка Wi-Fi, годинник, погода з HA).
3. **Повний контроль периферії:** Довільне програмне керування RGB-світлодіодами світлофора та поліфонічним зумером (сповіщення, звуки тривог із Home Assistant).
4. **100% бездротове оновлення (Full OTA):** Після одноразового збирання заліза всі наступні оновлення обох мікроконтролерів (ESP32 та GD32) відбуваються **виключно по повітрю (Wi-Fi OTA)**.

## 2. Апаратна платформа (Hardware Baseline)

Пристрій базується на материнській платі **`Storm Shadow Main Board REV3 20210610`**.

```
                           ┌────────────────────────┐
                           │   Home Assistant / UI  │
                           └───────────▲────────────┘
                                       │ Wi-Fi (ESPHome API / OTA)
                                       ▼
                     ┌────────────────────────────────────┐
                     │         ESP32-WROOM-32E            │
                     │  - 240 MHz Dual-Core, 4 MB Flash   │
                     │  - Мозок: ESPHome, LVGL, Wi-Fi OTA │
                     │  - OTA GD32 по UART (ROM-loader)   │
                     └─────────────────▲──────────────────┘
        Швидкий UART                   │
  (921600 baud, кадри/сенсори,         │       Зовнішній SWD-пробник (Pico/CMSIS-DAP)
   рутинне OTA через ROM-loader)       │       на TP16/TP17 — вручну, лише для
                                       ▼       першого заливу та unbrick
                     ┌────────────────────────────────────┐  ◄╌ TP16/TP17 (припаюється за потреби)
                     │          GD32F150C8T6              │
                     │  - 72 MHz Cortex-M3, 64 KB Flash   │
                     │  - Драйвер I/O, DMA-растеризатор   │
                     └───────┬─────────┬─────────┬────────┘
                             │         │         │
                   ┌─────────▼┐   ┌────▼────┐   ┌▼──────────────┐
                   │  Дисплей │   │ Сенсори │   │ Індикація/Звук│
                   │  240x240 │   │ NDIR CO2│   │ 3x LED        │
                   │  ST7789  │   │ SHT30 T/H│   │ Зумер (PWM)   │
                   └──────────┘   └─────────┘   └───────────────┘
```

### 2.1. Чіп 1: GD32F150C8T6 (Периферійний I/O співпроцесор)
* **Ядро:** ARM Cortex-M3 @ 72 MHz.
* **Пам'ять:** 64 KB Flash, **8 KB SRAM** (звірено з дампом: SP = `0x20001038`, вільно ≈ 4 КБ — замало для фреймбуфера 240×240×2 = 115 КБ, наслідки див. §4.2).
* **Підключена периферія:**
  * **Дисплей:** 240×240 кольоровий IPS TFT, контролер ST7789. **100% верифіковано на залізі**: 3-wire 9-bit SPI бітбенг (`PB12` RES, `PB13` SCK, `PB14` CS, `PB15` SDA, `PB8` Backlight HIGH/PWM). Відмальовано патерни з нульовим зсувом (0,0) RGB565.
  * **Сенсор CO₂:** **Honeywell CRIR M1 (`C06-0801-000`)**. **100% верифіковано на залізі**: USART0 (`PA9` TX, `PA10` RX @ 9600 8N1), `PB11` (5V Boost enable), `PB9` (Pwr switch). Опитування Modbus RTU Cmd #0 `FE 04 00 07 00 01 94 04` → CO₂ ppm зчитується стабільно.
  * **Сенсор T/H:** **Sensirion SHT30**. **100% верифіковано на залізі**: бітбенг-I2C (`PB6` SCL, `PB7` SDA), `PB2` (Sensor Pwr/Pullup); `PA8` — НЕ nRESET сенсора, а RESET ESP32 (див. GD32_HARDWARE_MAP §5), сенсор його не потребує, адреса `0x44` (ART/Periodic 0xE000).
  * **Зумер:** `LS1` на **`PB0`** (`TIMER2_CH2`, резонанс 2304 Hz). **100% верифіковано на залізі**.
  * **Світлодіоди індикації:** `PC14` (2×G), `PB4` (1×Y), `PB5` (2×R) + анодний ключ `PA1=1`. **100% верифіковано на залізі**.
  * **Кнопка:** `SW1` на **`PA0`** (Active-HIGH, підтяжка на платі до GND). **100% верифіковано на залізі**.
  * **Моніторинг живлення:** `PC15=1` (Main DC-DC), `PB3=1` (Periph rail), `PA1=1` (VLED).
  * **Зовнішня Flash:** Winbond 25Q32 (4 МБ SPI Flash, `U4`) на `PA4` (CS), `PA5` (SCK), `PA6` (MISO), `PA7` (MOSI).

### 2.2. Чіп 2: ESP32-WROOM-32E (Головний обчислювальний модуль)
* **Ядро:** Двоядерний Xtensa LX6 @ 240 MHz.
* **Пам'ять:** 4 МБ SPI Flash, 520 КБ SRAM.
* **Бездротові інтерфейси:** Wi-Fi 802.11 b/g/n, Bluetooth 4.2 / BLE.
* **Штатні лінії міжпроцесорного зв'язку (з GD32):**
  * `GPIO16` (ESP32 RX) ← `PA2` (GD32 TX, нога 12)
  * `GPIO17` (ESP32 TX) → `PA3` (GD32 RX, нога 13)
  * `GPIO15` (CTS), `GPIO14` (RTS)

## 3. Апаратні модифікації (Hardware Modification)

Модифікація виконується **одноразово** при першому розбиранні корпусу.

### 3.1. Первинна прошивка ESP32 (заливка базового ESPHome)
1. Тимчасово підпаяти 3 дроти USB-UART адаптера:
   * **`GND`** → Земля плати (екран USB).
   * **`TXD0`** (ESP32 Pin 35 / GPIO1) → RX перехідника.
   * **`RXD0`** (ESP32 Pin 34 / GPIO3) → TX перехідника.
2. Вхід у режим прошивки (Download Mode):
   * Замкнути **`GPIO0`** на `GND` (пінцетом або дротиком).
   * Подати живлення 5V через штатний роз'єм micro-USB.
   * *(Пін `EN` чіпати НЕ потрібно!)*
3. Прошити стартовий бінарник ESPHome через `esphome run`.
4. Відпаяти сервісні дроти `TX0`/`RX0`.

### 3.2. Прошивка GD32 через зовнішній SWD-пробник (без внутрішніх перемичок)
**ESP32 не задіяний як SWD-програматор.** SWD потрібен лише для **першого заливу прошивки GD32 та аварійного відновлення (unbrick)**; рутинне OTA йде по існуючому UART через ROM-loader (§7.3). Тому замість постійних внутрішніх перемичок — зовнішній пробник, який припаюється до тестових точок за потреби (саме так робився заводський дамп):
* **Пробник:** Raspberry Pi Pico з прошивкою debugprobe (CMSIS-DAP) + OpenOCD (див. [`tools/swd/README.md`](../tools/swd/README.md)).
* **Підключення** (три дроти, тимчасово):
  1. `TP16` (GD32 `PA14` / **SWCLK**) → Pico `GP2`.
  2. `TP17` (GD32 `PA13` / **SWDIO**) → Pico `GP3`.
  3. `GND` → Pico `GND`.
* **Під час розробки** пробник зручно залишати припаяним — це дає і швидку ітерацію прошивки GD32, і миттєвий unbrick без повторного паяння.
* **У «продакшн»-складанні** пробник відпаюється; якщо колись знадобиться розцеглити пристрій — TP16/TP17 припаюються повторно.

## 4. Архітектура програмного забезпечення

### 4.1. Прошивка ESP32 (Платформа: ESPHome)
ESP32 бере на себе 90% функціоналу системи:
1. **Зв'язок з Home Assistant:**
   * Автоматичне виявлення всіх сутностей (сенсори CO₂, температури, вологості, батареї, заряду).
   * Сервіси для відтворення звуків, встановлення порогів тривоги.
   * Отримання точного часу по SNTP та локальної погоди з HA.
   * **Первинний provisioning Wi-Fi — штатними засобами ESPHome** (заводський BLE не використовується): `wifi:` з `ap:` fallback + `captive_portal:`; опційно `improv_serial` на етапі складання. Креди — у NVS (§9.1).
   * **Оцінка порогів тривоги — на ESP32** (не на GD32), працює й **без Wi-Fi**: ESP32 має покази CO₂ від GD32 і сам керує LED/зумером (§9.2).
2. **Графічний рушій LVGL:**
   * Рендеринг повного кадру в оперативній пам'яті ESP32 (115 КБ фреймбуфер).
   * Відстеження брудних прямокутників (Dirty Rectangles) для надшвидкого оновлення окремих чисел без перезаливки всього кадру.
3. **Драйвер обміну з GD32 (Custom C++ Component):**
   * Обмін даними по UART на швидкості **921 600 бод**.
   * Прийом пакетів телеметрії від GD32 (виміри сенсорів).
   * Передача команд відображення (пакети пікселів/прямокутників) на дисплей.
4. **UART OTA GD32 через ROM-loader (`gd32_uart_ota.h`):**
   * Staging образу в ESP32, гейти (CRC + батарея), команда `CMD_ENTER_BOOTLOADER`, потім заливка по `PA2`/`PA3` штатним протоколом ROM-завантажувача (§7.3).
   * Кнопка/сервіс у HA «Оновити прошивку GD32» із завантаженням файлу `.bin`.
   * *(Перший залив і unbrick — зовнішнім SWD-пробником, поза ESP32; див. §3.2, §7.2, §7.4.)*

### 4.2. Прошивка GD32F150 (Платформа: PlatformIO + GD32 SPL / Arduino-GD32)

> **Звірено з дампом `tools/swd/gd32_flash.bin` (64 КБ, зайнято ~90%):** більша частина заводської прошивки GD32 — це оркестрація ESP-AT модема (рядки `AT+CWJAP=`, `AT+MQTTUSERCFG=`, `AT+MQTTCONN=`, `AT+BLEINIT`, endpoint `ssco2-dev.honcloud.honeywell.com.cn`, кодове ім'я `Storm_Shadow`; WiFi-креди `TP-Link_B55B` / `3151831518` та адреса брокера лежать в останній сторінці flash `0xFC00…0xFFFF`). У новій архітектурі **вся ця логіка видаляється**: WiFi/MQTT/BLE тепер веде ESP32 (він і є радіо), тож GD32 звільняється від ~60% свого коду, частини flash і кількох пінів.

**Уточнення щодо «писати з нуля».** Драйвери вручну писати НЕ треба — вони готові:
* **База:** офіційна **GD32F1x0 Firmware Library (SPL)** від GigaDevice (RCU, GPIO, USART, SPI, DMA, I2C, TIMER-PWM, ADC, FMC) — або **Arduino-GD32 core** (CommunityGD32Cores) під PlatformIO.
* **Дисплей ST7789:** заводська init-послідовність, розпіновка (PB13/14/15) і low-level функції **вже витягнуті з дампа** → [`GD32_HARDWARE_MAP.md`](GD32_HARDWARE_MAP.md) §2. Драйвер пишемо під реальні піни (бітбенг або HW-SPI1).
* **CO₂ (Honeywell CRIR M1):** UART **Modbus RTU** (9600 8N1). CRIR — Senseair-похідний, тож стартова точка — S8-сумісний кадр читання `FE 04 00 03 00 01` (func `0x04`, вхідний регістр CO₂, CRC-16 Modbus); точна адреса регістра — з «CRIR M1 User Guide». Готові Senseair/Modbus бібліотеки як референс.
* **T/H (SHT30):** офіційний Sensirion `embedded-sht` (апаратно-незалежний C) або Arduino-lib SHT3x; I2C `0x44`, CRC-8.

Тобто ~80% коду GD32 — готові драйвери; писати доведеться лише «клей»: парсер UART-протоколу з CRC, планувальник телеметрії, шлях `DRAW_RECT → ST7789 DMA`, обробники LED/зумера/підсвітки. Обсяг — помірний прошивковий проєкт, але не «залив бібліотеку — і готово».

**Жорсткі обмеження (звірено з залізом):**
* **8 КБ SRAM (SP = `0x20001038`, стек ~4 КБ).** Фреймбуфер 115 КБ фізично не влазить → **LVGL і будь-який композитинг напівпрозорості на GD32 неможливі**; GD32 лише стрімить готові RGB565-пікселі від ESP32 у ST7789 через DMA.
* **Бажано не переналаштовувати `PA13`/`PA14` як GPIO** — це SWDIO/SWCLK (`TP17`/`TP16`), канал заливу й unbrick зовнішнім пробником. Якщо їх усе ж зайняти, зовнішній пробник ще зможе перехопити чип через *connect-under-reset* (утримання NRST при під'єднанні), але це складніше — простіше лишити SWD-піни вільними.

> **Звірено з дампом — яка периферія й як задіяна** (скан базових адрес у `gd32_flash.bin` + дизасемблер):
> * **UART0 + UART1 (апаратні)** — один канал до ESP32 (115200), другий до CO₂-сенсора (Modbus). ✓
> * **Дисплей ST7789 — бітбенг по GPIO** (апаратних SPI0/SPI1 у прошивці **не** задіяно). Це **не проблема**: вузьке місце — UART-канал до ESP32 (~92 КБ/с), тож навіть бітбенг-блит його випереджає. Апаратний SPI+DMA (п.1 нижче) застосуємо, лише якщо піни дисплея лежать на SPI-периферії — треба простежити піни; інакше лишаємо бітбенг (швидкості вистачає).
> * **SHT3x — бітбенг I2C** (апаратних I2C0/I2C1 не задіяно). Драйвиться тривіально (бітбенг або HW I2C).
> * **FWDGT (IWDG) задіяний** — підтверджує здійсненність §9.3.
> * Базу ADC не знайдено — метод вимірювання батареї уточнити на бенчі.

Функції прошивки GD32 (максимально полегшена, без бізнес-логіки):
1. **DMA-растеризатор дисплея:**
   * Слухає потік UART. При надходженні команди `DRAW_RECT(x, y, w, h, pixels)` — через апаратний SPI DMA «виливає» пікселі прямо в пам'ять контролера ST7789 без проміжних буферів.
2. **Драйвер сенсорів:**
   * Фоновий збір даних: читання NDIR-сенсора CO₂ (UART), опитування SHT3x (I2C), читання напруги АКБ (АЦП).
   * Періодична відправка короткого двійкового пакета (16–20 байт) на ESP32 кожні 1–2 секунди.
3. **Драйвер індикації (тупий виконавець, без бізнес-логіки):**
   * Прийом команд на встановлення яскравості підсвітки (PWM).
   * Керування RGB-світлодіодами світлофора **за прямою командою ESP32** — GD32 сам пороги CO₂ не оцінює й не тримає (§9.2).
   * Генерація тонів на зумері `LS1` за запитом від ESP32 (частота + тривалість).
4. **Незалежний watchdog (IWDG):**
   * GD32 «гладить» IWDG у головному циклі; при зависанні — самоскид. Це **єдина** автострахова від зависання, бо ESP32 не має лінії reset до GD32 (§9.3).
5. **Хук OTA (вхід у ROM-loader):**
   * Обробка команди `CMD_ENTER_BOOTLOADER` (§5.2): коректно зупинити периферію/DMA і зробити jump у system memory (`0x1FFF EC00`) — це вмикає рутинне UART-OTA по `PA2`/`PA3` (§7.3).
   * Бажано лишити `PA13`/`PA14` (SWDIO/SWCLK) вільними — для заливу/unbrick зовнішнім пробником (§3.2).

## 5. Протокол міжпроцесорного обміну (UART 921 600 бод)

Бінарний протокол із контрольною сумою для швидкого та надійного зв'язку.

> **Пропускна здатність.** 921 600 бод (8N1) = **≈ 92 КБ/с**. Дисплей висить на GD32, тож кожен піксель UI йде каналом ESP32→GD32. Орієнтири: блок цифр CO₂ ~120×70 ≈ 17 КБ ⇒ ~0,2 с; область графіка ~240×120 ≈ 57 КБ ⇒ ~0,6 с; повний кадр 115 КБ ⇒ ~1,25 с. За робочого сценарію (цифри раз на 1–2 с «брудним» прямокутником, графік на тлі раз на ~хвилину) канал завантажений на одиниці відсотків — **запасу вистачає з головою**. З True-Black тлом навіть повний кадр стискається простим RLE до ~20–40 КБ (довгі прогони `0x0000`) ⇒ ~0,3 с. У бюджет **не влазить лише суцільна анімація високого FPS** (плавний скрол тла щокадру) — але вона й не потрібна.
> * **Апаратний flow-control обов'язковий:** штатні `CTS = GPIO15` / `RTS = GPIO14` мають бути задіяні — на 921 600 з фоновим стрімінгом пікселів без RTS/CTS буде переповнення FIFO.
> * **CRC — єдиний і точно визначений:** CRC-16-CCITT, поліном `0x1021`, init `0x0000`, MSB-first, над усіма байтами між Magic і полем CRC (як у downlink §8f репозиторію). У проєкті вже співіснують два різні CRC-16 (`0x8005` для BLE, `0x1021` для downlink) — тут фіксуємо саме `0x1021`, щоб уникнути розбіжностей між чіпами.

### 5.1. Пакети GD32 → ESP32 (Uplink Telemetry, кожні 1-2 с)
| Байт | Поле | Опис |
|---|---|---|
| `0..1` | Magic | `0xAA 0x55` |
| `2` | Packet Type | `0x01` (Telemetry) |
| `3..4` | CO2 | uint16 LE (ppm) |
| `5..6` | Temp | int16 LE (0.01 °C) |
| `7..8` | Humidity | uint16 LE (0.01 %) |
| `9..10`| Battery mV | uint16 LE (мВ) |
| `11` | Status | Bit 0: Charging, Bit 1: USB present, Bit 2: Warm-up, Bit 3: Sensor fault, Bit 4: Button, **Bit 5: LED green, Bit 6: LED yellow, Bit 7: LED red** |
| `12..13`| CRC-16 | Контрольна сума |

> **Синхронізація стану (реалізовано).** Біти 5–7 віддають **живий стан LED** — GD32 є джерелом істини (він запалює зелений при старті), а ESP дзеркалить ці біти на switch-сутності в HA. Так HA показує реальний стан панелі. USB/Charging (біти 0–1) виведені окремими binary-сенсорами; з `Battery mV` ESP рахує ще й % заряду.

> **Хендшейк версій + build-stamp (реалізовано).** Пакет `Packet Type = 0x02` (Hello) розширено: `[Magic][0x02][protocol_version: uint8][gd32_fw_version: uint16][build_flags: uint8][build_epoch: uint32 LE][git_hash: uint32 LE][CRC-16]` (17 байтів). GD32 шле його **періодично** (раз на цикл телеметрії), бо ESP живиться від PF7-рейки й вантажиться після старту GD32. ESP формує рядок версії `X.Y.Z g<hash>[+] (YYYY-MM-DD HH:MM UTC)` у сутність «GD32 Firmware» (`+` = брудне дерево на момент збірки).

### 5.2. Пакети ESP32 → GD32 (Downlink Commands)
1. **`CMD_DRAW_RECT` (`0x10`):** Оновлення частини екрана.
   * `[Header 0xAA 0x55] [0x10] [X: uint8] [Y: uint8] [W: uint8] [H: uint8] [Length: uint16] [Pixel Data: RGB565...] [CRC16]`
2. **`CMD_SET_BACKLIGHT` (`0x11`):** Яскравість підсвітки (0..100%). Реалізовано апаратним PWM на `PB8 = TIMER15_CH0` — лінійний димінг.
3. **`CMD_SET_LEDS` (`0x12`):** Стан світлодіодів (Червоний / Жовтий / Зелений / Яскравість). **Яскравість ігнорується** — залізо не підтримує димінг індикаторних LED (спільна рейка VLED з конденсатором); лише on/off. Байт лишено для сумісності формату.
4. **`CMD_BEEP` (`0x13`):** Звуковий сигнал (Частота в Гц + тривалість у мс). **Не-блокуючий**: тон генерується `PB0 = TIMER2_CH2` PWM, тривалість відлічує main-loop.
5. **`CMD_PLAY_MELODY` (`0x14`):** Програвання мелодії без блокування. `[Header 0xAA 0x55] [0x14] [Count: uint8] [Count × (Freq: uint16 LE, Dur_ms: uint16 LE)] [CRC16]`. GD32 стрімить ноти в обмежений буфер (як `DRAW_RECT`, до 96 нот), програє через таймер + тік main-loop. `Freq = 0` — пауза; `Count = 0` — стоп/тиша. Мелодії надходять **з HA**: ESPHome-служби `play_rtttl(song)` / `play_anthem` / `stop_melody` — ESP парсить **RTTTL**-рядок у ноти й стрімить сюди (нотні дані не хардкодяться на GD32).
6. **`CMD_ENTER_BOOTLOADER` (`0x1F`):** Запит на рутинне UART-OTA (§7.3). GD32 зупиняє периферію/DMA і робить jump у ROM-loader (system memory `0x1FFF EC00`); подальший обмін веде вже сам ROM-завантажувач своїм протоколом. Рекомендовано вимагати «магічне» підтвердження в payload, щоб виключити випадковий вхід.

## 6. Вимоги до інтерфейсу користувача (UI/UX)

> **Обраний напрям — Варіант A** (підтверджено на макеті): велике адаптивне число CO₂ по центру + напівпрозорий графік динаміки на тлі, **без** заводської дугової шкали. Контент компонується в колі, вписаному в матрицю 240×240 (кути ховаються під круглою чорною рамкою). Правки очікуються, але дух саме такий.

> **Узгодження з каналом (§5):** графік на тлі оновлюється **періодично** (раз на ~хвилину — цілком достатньо, бо новий семпл CO₂ з'являється рідко), а блок цифр — раз на 1–2 с окремим «брудним» прямокутником. Такий режим вкладається в канал UART із великим запасом, окремий SPI-лінк **не потрібен**. SPI-лінк варто розглядати лише в гіпотетичному разі, якщо колись знадобиться саме плавна безперервна анімація тла (щокадровий скрол).

1. **Загальна стилістика:**
   * Глибокий чорний фон (True Black під IPS матрицю).
   * Відсутність видимих рамок та "швів" дисплея.
2. **Головний екран:**
   * **Центр:** Велике, висококонтрастне число CO₂ (шрифт Roboto/Inter Bold, висота 50–60 px).
   * **Тло цифр:** Плавний напівпрозорий графік динаміки (Area Chart) за останні 4–6 годин із градієнтним заповненням униз.
   * **Колірна диференціація (Adaptive Theme):**
     * `< 800 ppm`: Смарагдово-зелений акцент.
     * `800 .. 1000 ppm`: Теплий бурштиновий акцент.
     * `> 1000 ppm`: Насичений рубіново-червоний акцент.
   * **Верхній статус-бар:**
     * Поточний час (з точністю до хвилини).
     * Значок підключення Wi-Fi (з відображенням сили сигналу).
     * Значок батареї / блискавка заряду.
   * **Нижній бар:**
     * Компактні плашки: Внутрішня температура + вологість.
     * Опціонально: Вулична температура або погода з Home Assistant.
3. **Деградовані стани** (замість «замороженого» екрана; поведінка — §9.5):
   * **Прогрів сенсора** (перша ~хвилина, warm-up пакети відкидаються) — напис «Прогрів…» замість числа.
   * **Немає зв'язку з GD32** (таймаут UART) — індикатор помилки, останні дані сірим/застарілими.
   * **Wi-Fi/HA недоступні** — перекреслена іконка Wi-Fi; локальні показники працюють далі.
   * **Критична батарея** — попередження + зниження яскравості.
   * **OTA в процесі** — екран прогресу прошивки.
   * **Несумісні версії прошивок** (§9.6) — попередження, базовий режим.

## 7. Процедура оновлення (OTA & Unbricking Strategy)

Стратегія **двошляхова**: штатне OTA GD32 йде **по існуючому міжчиповому UART через заводський ROM-завантажувач** (без участі ESP32-SWD), а **зовнішній SWD-пробник використовується лише для першого заливу та аварійного відновлення**, вручну (§3.2).

### 7.1. Оновлення ESP32
Стандартний ESPHome OTA через Home Assistant.

### 7.2. Перший залив прошивки GD32 (одноразово) — зовнішнім SWD-пробником
Заводський GD32 має RDP1 і **не вміє входити в ROM-loader програмно**, тож перший залив можливий лише апаратно:
* Зовнішній пробник (Pico + OpenOCD) на `TP16`/`TP17` знімає RDP через `unlock` (це **mass-erase**, стирає заводську прошивку і скидає option bytes) і заливає нашу прошивку GD32 вже без RDP.
* Під час розробки пробник лишається припаяним — залив GD32 іде безпосередньо ним, швидко (див. §3.2).
* **Образ відновлення** заводського стану — дамп [`tools/swd/gd32_flash.bin`](../tools/swd/gd32_flash.bin) (WiFi-креди вшиті в останню сторінку flash цього дампа).

### 7.3. Рутинне OTA GD32 — по UART через резидентний завантажувач (основний шлях)
Доступне **після** першого заливу нашої прошивки. 

> **⚠️ Відмова від заводського ROM-завантажувача (`0x1FFFEC00`):**
> Реверс-інжиніринг заводського ROM GD32F150C8T6 виявив апаратну помилку маски (Silicon Errata): при надсиланні `0x7F` на `PA3` код завантажувача вимірює бодрейт, але ініціалізує регістри **USART0** замість USART1 і відповідає `0x79` на пін `PA9` (сенсор CO₂), лишаючи лінію `PA2` (до ESP32) мертвою. Через це штатний ROM-завантажувач апаратно непридатний для роботи на лінку `PA2`/`PA3`.

**Новий підхід: Власний резидентний завантажувач (SRAM / Dual-stage Flash):**
1. **Staging.** ESP32 завантажує весь образ `gd32_firmware.bin` (Wi-Fi/HA) у власне сховище (окрема flash-партиція або DRAM — 64 КБ влазить). Обрив Wi-Fi на цій фазі **не чіпає flash GD32** — просто повтор завантаження.
2. **Гейт-перевірки перед стиранням** (жодного стирання flash, поки всі не пройдені):
   * **CRC/хеш** стейджнутого образу збігається з очікуваним;
   * **підключене зовнішнє живлення** або **заряд батареї ≥ 3500 мВ**;
   * Розмір образу є валідним (до 64 КБ).
3. **Software-jump у резидентний флешер.** ESP32 шле по `PA2`/`PA3` команду `CMD_ENTER_BOOTLOADER` (`0x1F`, payload `0xDEADBEEF`). GD32 підтверджує отримання кадром ACK (`0xAA 0x55 0x1F 0x79 ...`), очікує завершення передачі по `USART_TC` і передає керування флешеру в оперативній пам'яті (SRAM).
4. **Flash.** Резидентний завантажувач у SRAM працює на `PA2`/`PA3` (USART1), приймає образ швидким протоколом (ST/GD-сумісні команди: 0x7F autobaud, 0x43 mass-erase, 0x31 write memory) або блоковим трансфером і прошиває Flash-пам'ять.
   * Час заливки всієї прошивки (~7 КБ) становить **1.5–1.8 секунди**.
   * SWD-лінія **не блокується** (на відміну від заводського ROM-loader).
5. **Reboot & verify.** GD32 запускає нову прошивку з адреси `0x08000000`; ESP32 переконується, що телеметрія відновилась.

### 7.4. Аварійне відновлення (Unbrick) — зовнішнім SWD-пробником, вручну
Крайовий випадок: живлення пропало посеред 1.5-секундного запису Flash.
* Припаяний або притиснутий зовнішній пробник (Pico на `TP16`/`TP17`/`GND`) за допомогою команди `python tools/swd/flash.py --swd-mem` прошиває GD32 з нуля за **1.8 секунди** у будь-якому стані ядра.

### 7.5. Архітектурне обґрунтування вибору
Відмова від закритого заводського ROM-loader на користь власного завантажувача:
* Усуває критичний апаратний дефект кремнію (переплутані USART0/USART1 на `PA3`).
* Дозволяє повноцінно логувати кожен крок процесу прямо в консоль ESPHome / Home Assistant.
* Зберігає працездатність SWD під час оновлення (не треба перезавантажувати чіп для перевірки стану).
* Забезпечує надвисоку швидкість прошивки (до 4 КБ/с).
* Для фінального продукту дозволяє виділити перші 2 КБ Flash під перманентний Golden Bootloader, що робить OTA 100% захищеним від збоїв живлення (unbrickable по повітрю).

## 8. Консольний доступ для агентів та віддалений дебаг (CLI-first & Remote Debug)

Принцип: **усі маніпуляції з прошивками та вся діагностика доступні з командного рядка** — без обов'язкового GUI Home Assistant. Після одноразового фізичного першого заливу (§3, §7.2) подальші операції (оновлення обох чипів, зчитування стану, траблшутінг) виконуються скриптовано — зокрема ШІ-агентом — локально по мережі та «по повітрю».

### 8.1. Канали доступу
* **ESPHome CLI** — базовий: `esphome compile/run/logs htram.yaml`. OTA і стрім логів працюють по Wi-Fi після першого заливу.
* **ESPHome Native API** (шифрований) — програмний доступ через `aioesphomeapi` (Python): виклик сервісів, читання сутностей, підписка на логи.
* **HTTP на ESP32** (`web_server` / кастомний хендлер) — для операцій, незручних через API (заливка бінарника GD32): дружній до `curl`.
* *(Опційно)* **MQTT** — команди/статус через топіки, якщо потрібна інтеграція з наявним брокером.

Усі канали — **лише локальна мережа**, під захистом ключа API + OTA-пароля.

### 8.2. Операції з прошивками з консолі
| Операція | Команда (приклад) | Транспорт |
|---|---|---|
| Прошити/оновити ESP32 (OTA) | `esphome run htram.yaml` | ESPHome OTA |
| Логи ESP32 (стрім, OTA) | `esphome logs htram.yaml` | API/OTA |
| Оновити прошивку GD32 (OTA) | `htram gd32-flash gd32_firmware.bin` | HTTP POST → staging + гейти + ROM-loader (§7.3) |
| Статус останнього OTA GD32 | `htram gd32-status` | API/HTTP (прогрес, код помилки) |
| Скинути/перезапустити GD32 | `htram gd32-reset` | API-сервіс → `CMD_*` по UART |

* Заливка GD32 повертає структурований результат (JSON): `staged_crc`, `battery_mv`, `gate_passed`, `bytes_written`, `verify_ok`, `result`.
* **Hard-brick по повітрю не відновлюється** — потрібен фізичний пробник (це робить користувач, не агент; §7.4).

### 8.3. Діагностичні сутності (read-only, з CLI/HA)
Експонуються як ESPHome sensor/text_sensor — видно і в `esphome logs`, і через API:
* `gd32_fw_version`, `esp_fw_version`, `uptime`, `free_heap`, `wifi_rssi`.
* `last_telemetry_hex` — останній сирий пакет GD32→ESP32 (для звірки протоколу).
* `uart_crc_errors`, `uart_frame_errors`, `uart_rx_timeouts` — лічильники якості лінка.
* `last_gd32_ota_result`, `battery_mv`, `charging`.

### 8.4. Команди дебагу/траблшутінгу (services)
Викликаються з CLI (через `aioesphomeapi` / HA-сервіс / MQTT):
* `beep(freq_hz, ms)`, `set_leds(r,g,y,bright)`, `set_backlight(pct)` — перевірка периферії наживо.
* `draw_test_pattern()` — тест дисплея/каналу (кольорові смуги, CRC round-trip).
* `uart_sniffer(on|off)` — режим, що дампить сирі кадри GD32↔ESP32 у лог (hex) для аналізу агентом.
* `send_raw_uart(hex)` — інжекція довільного кадру на GD32 (за прапорцем-guard; для реверсу/дебагу протоколу).
* `gd32_enter_bootloader()` — ручний вхід у ROM-loader (для дебагу шляху OTA).
* `calibrate_co2()` / `set_abc_period(days)` — ручне калібрування NDIR «на свіжому повітрі» та період ABC (§9.4).
* `selftest()` — пінг GD32, перевірка живості сенсорів/дисплея; повертає звіт-рядок.

### 8.5. Єдина утиліта-обгортка
`tools/htram.py` — один entrypoint для агента: `htram {logs,status,selftest,flash-esp,flash-gd32,gd32-status,gd32-reset,beep,leds,sniff,raw}`. Адресу/ключі бере з env або `.htram.toml`. Кожна **деструктивна** підкоманда (`flash-*`, `raw`, `gd32-enter-bootloader`) вимагає `--yes` або інтерактивного підтвердження.

### 8.6. Застереження щодо доступу агента
* Деструктивні операції (заливка, `enter_bootloader`, `send_raw_uart`) проходять ті самі гейти (CRC + батарея, §7.3) і за замовчуванням вимагають явного підтвердження.
* Безпека/приватність: доступ лише в локальному сегменті мережі; ключі не логуються; сирі дампи телеметрії не виносяться за межі мережі без запиту.

## 9. Поведінка системи, стани та надійність

### 9.1. Первинний provisioning Wi-Fi
Штатними засобами ESPHome (заводський BLE-провізіонінг не використовується):
* `wifi:` з `ap:` fallback + `captive_portal:` — якщо не під'єднався до збереженої мережі, підіймає власну точку доступу з формою вводу SSID/пароля.
* *(опц.)* `improv_serial` для первинного налаштування через USB на етапі складання.
* Креди зберігаються у NVS ESP32; скид/переналаштування — через кнопку або HA-сервіс.

### 9.2. Логіка тривоги — на ESP32 (працює офлайн)
Пороги CO₂ оцінює **ESP32** і сам керує світлофором/зумером через GD32. Це **не залежить від Wi-Fi**: ESP32 отримує покази CO₂ від GD32 по UART і надсилає назад `CMD_SET_LEDS` / `CMD_BEEP`. Wi-Fi потрібен лише для інтеграції з HA та зміни налаштувань.
* Тобто тривога фактично **локальна/автономна на рівні пристрою** — просто рахується на ESP32, а не на GD32. Дублювати цю логіку в GD32 **не потрібно**.
* Єдиний момент, коли алярм не оцінюється, — якщо сам ESP32 перезавантажується (напр. під час власного OTA, ~10–20 с) або завис. Це та сама єдина точка відмови, що й для всього UI; прийнятно.
* GD32 порогів не тримає й не оцінює — лише виконує команди LED/зумера.

### 9.3. Watchdog та відновлення GD32
Оскільки ESP32 не має лінії reset до GD32 (SWD-перемички прибрано), єдина автострахова від зависання GD32 — **його власний незалежний watchdog (IWDG)**: GD32 періодично «гладить» IWDG у головному циклі; при зависанні — самоскид. ESP32 додатково детектує тишу телеметрії (таймаут) і показує деградований стан (§6, §9.5). Повний unbrick (якщо і IWDG не рятує) — зовнішнім пробником (§7.4).

### 9.4. Калібрування NDIR-сенсора
CRIR M1 має заводське калібрування та автоматичне калібрування базової лінії (**ABC**, підлаштовує нуль до ~400 ppm) — за замовчуванням покладаємось на них.
* Якщо сенсор дрейфує — передбачити **ручне калібрування нульової точки «на свіжому повітрі»** (~400 ppm) та вмикання/період ABC через Modbus-регістри CRIR M1 (User Guide).
* Виноситься сервісами в CLI/HA: `calibrate_co2`, `set_abc_period` (§8.4).

### 9.5. Деградовані стани
Явні стани замість «замороженого» екрана (відображення — §6):
* **Прогрів сенсора** (перша ~хвилина, warm-up пакети відкидаються; біт 2 у Status телеметрії §5.1).
* **Немає зв'язку з GD32** — таймаут UART → індикатор помилки, дані застарілими.
* **Wi-Fi/HA недоступні** — перекреслена іконка Wi-Fi; локальні показники працюють.
* **Критична батарея** — попередження + зниження яскравості.
* **OTA в процесі** — екран-заставка прогресу.

### 9.6. Версійність і сумісність прошивок
Протокол ESP32↔GD32 еволюціонує → **хендшейк версій на старті** (пакет `0x02` Hello, §5.1):
* GD32 повідомляє `protocol_version`; ESP32 звіряє з очікуваним.
* При розбіжності — деградований режим (базова телеметрія без нових команд) + попередження в лог/HA, без краху.

### 9.7. Збереження та синхронізація налаштувань
* Джерело правди — **ESP32** (ESPHome preferences/NVS): пороги тривоги, одиниці (°C/°F), яскравість, auto-screen-off.
* При завантаженні/зміні ESP32 пушить у GD32 лише те, що той виконує (яскравість, стан LED). Пороги в GD32 не зберігаються (наслідок §9.2).

### 9.8. Фізична кнопка (`SW1`)
Кнопку на корпусі використовуємо. Кнопка `SW1` фізично на платі; її стан GD32 передає в телеметрії (окремий біт/подія), а логіку обробляє ESP32. Пропонована схема (адаптується):
* **Коротке натискання** — перемикання екранів/режиму (головний → великий графік → деталі).
* **Довге (~2 с)** — примусове ввімкнення/вимкнення підсвітки.
* **Дуже довге (~10 с)** — скид Wi-Fi provisioning (повернення до captive-portal, §9.1).
* Калібрування CO₂ навмисно **не** вішаємо на кнопку (щоб не спрацювало випадково) — лише через CLI/HA-сервіс (§8.4, §9.4).

### 9.9. Зовнішні дані з Home Assistant (опційно)
Має бути **можливість** виводити на екран дані з HA (напр. вулична температура/погода), але конкретний склад — TBD.
* Реалізація: конфігурований «слот» даних з HA (значення будь-якої сутності HA, що ESP32 отримує по Native API) — окремий рядок у нижньому барі або окремий екран (перемикається кнопкою §9.8).
* За замовчуванням вимкнено; вмикається й наповнюється пізніше без зміни архітектури.

## 10. Етапи реалізації (Roadmap)

* [ ] **Етап 1 (Залізо):** Сенсор CO₂ підтверджено — **Honeywell CRIR M1** (§2.1); лишається звірити Modbus-регістр CO₂ та піни дисплея (HW-SPI vs бітбенг); підготовка зовнішнього SWD-пробника (Pico + OpenOCD) і тестове під'єднання до `TP16`/`TP17`/`GND`. Внутрішні перемички ESP32→SWD **не паяються**.
* [ ] **Етап 2 (GD32 Driver):** Створення каркаса проекту PlatformIO для GD32F150:
  * Ініціалізація UART на 921 600 бод.
  * DMA-виведення на дисплей ST7789.
  * Читання датчиків CO₂ та SHT3x.
  * Хук `CMD_ENTER_BOOTLOADER` → jump у ROM-loader (`0x1FFF EC00`).
* [ ] **Етап 3 (ESP32 UART OTA):** `gd32_uart_ota.h` — staging образу, гейти CRC + батарея, команда `CMD_ENTER_BOOTLOADER`, заливка по `PA2`/`PA3` протоколом ROM-loader. *(Перший залив/unbrick — зовнішнім пробником, окремого ESP32-SWD компонента немає.)*
* [ ] **Етап 4 (UI / LVGL):** Верстка та налаштування стильного інтерфейсу LVGL в ESPHome.
* [ ] **Етап 5 (Фінал):** Інтеграція в Home Assistant та тестування стабільності.
* [ ] **Етап 6 (CLI / агентський доступ):** утиліта `tools/htram.py`, HTTP-ендпоінт заливки GD32, діагностичні сутності та debug-сервіси (§8). Бажано вести паралельно з Етапами 3–5, щоб дебажити консоллю з самого початку.

## 11. Узгоджені рішення (журнал)

Раніше відкриті питання — тепер закриті:
1. **Датчик CO₂:** **Honeywell CRIR M1 (`C06-0801-000`)** — підтверджено маркуванням; даташит у репо (`CO2_CRIR_M1.pdf`). Протокол UART Modbus RTU (§2.1, §4.2). Точна реєстрова адреса CO₂ — з CRIR M1 User Guide.
2. **Фізична кнопка:** **використовуємо** — коротке/довге/дуже-довге натискання (§9.8).
3. **Зовнішні дані з HA:** **можливість має бути**, конкретний склад — пізніше; реалізуємо як конфігурований слот (§9.9).
4. **Гейт OTA GD32:** вимагаємо **підключене зовнішнє живлення + заряд ≥ 50%** (§7.3). Питання внутрішніх SWD-перемичок знято — залив/unbrick зовнішнім пробником (§3.2).

**Ще відкрите / TBD:** точний склад зовнішніх даних з HA; точна Modbus-адреса регістра CO₂ CRIR M1 (User Guide/бенч); чи піни дисплея на HW-SPI (§4.2); метод вимірювання батареї; конкретні пороги тривоги CO₂ (дефолт 800/1000 ppm).
